# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Truth of Auditor** — a Django 5.2 app that reconciles a betting/credit operator's records across four kinds of sources: the **Panel** (site's own DP/WD history), the **Bracket** (agent ledger), **Banks**, and payment **Gateways**. It ingests exported files (xlsx/csv/pdf, some encrypted), normalizes every row into one canonical `Transaction`, then matches credit-side records against money-side records to surface discrepancies. UI and code comments are in Indonesian; keep that convention.

## Commands

The virtualenv is at `.venv`. Activate it first: `source .venv/bin/activate`.

```bash
python manage.py test                         # run all tests (~850)
python manage.py test web.tests_reconcile     # one module
python manage.py test web.tests_reconcile.SomeTestCase.test_x   # one test
python manage.py runserver                     # dev server (sqlite, DEBUG=True)
python manage.py migrate                        # apply migrations (includes seed data)

# CLI equivalents of the core pipeline (useful for debugging without the UI):
python manage.py ingest <parser_key> <file_path> [--flow dp|wd] [--password ...]
python manage.py match <panel_bracket|panel_bank|bracket_bank> [--from YYYY-MM-DD] [--to YYYY-MM-DD]

# Fase-0 harness: ingest a folder of real exports + auto daily batches + match-rate report.
# Use this to calibrate matcher changes against real data BEFORE shipping.
python manage.py validate_brands --dir <folder> --toko <mul|g25|mxw|...> --flow-from-name
```

Reference data (SourceTypes, the "Default" ToleranceProfile, seeded Tokos) is created by **data migrations**, not fixtures — a fresh `migrate` gives you a working DB. Tests rely on these seeds existing.

To run anything against a throwaway DB (calibration, repros) without touching the dev DB, point `DATABASE_URL` at a scratch sqlite file: `DATABASE_URL=sqlite:////tmp/scratch.sqlite3 python manage.py migrate && ... validate_brands ...`.

## Architecture: the ingest → match pipeline

Everything flows through two stages. Understanding these two modules explains most of the codebase.

### 1. Ingest (`sources/`) — heterogeneous files → canonical `Transaction`

- **`sources/detect.py`** `detect_source(path, filename)` sniffs header tokens / extension and returns ranked `{parser_key, confidence}`. The web upload flow auto-detects, and only asks the user to confirm when confidence < 0.8.
- **`sources/services.py`** `ingest(parser_key, file_path, ...)` is the single entry point: picks the parser from the `PARSERS` dict, decrypts first if the file is an encrypted xlsx (OLE2 magic bytes → `msoffcrypto`, Mandiri e-statements), runs it, and bulk-creates `Transaction` rows inside one atomic block.
- **`sources/parsers/`** one class per format (`panel`, `bracket`, `banks.py` → BRI/BCA-CSV/Mandiri, `bca_pdf` + `bni_pdf` → bank e-statement PDFs (both emit `source_key="bank"`), `gateways.py` → NXPay/QRFlyer/RPay/QHoki, `cor.py` → COR/Gacor25 panel-bank/QRIS/QRIS-WD, `bonus.py` → panel_bonus/bracket_bonus). Each subclasses `BaseParser` and returns a list of dicts whose keys **exactly match `Transaction` fields**. Shared parsing helpers (decimal/date parsing for both `intl` and `id` number formats, ticket/ref regexes, `clean_name`, `row_hash`, the styles-tolerant `read_xlsx_rows`) live in **`sources/parsers/base.py`**.
- **Idempotency:** every row gets a `row_hash` (stable hash of key fields). `ingest` skips hashes that already exist for that `(source_type, toko)`, so re-importing the same file is safe. Skipped rows are additionally **linked** to the new upload via `Upload.duplicate_transactions` (M2M) — bank exports are often rolling/overlapping, and this link is what lets the Mutasi Bank per-file filter reconstruct the file's full content (uploads from before the field exist without links and fall back to attributed-rows-only).
- **"Ketiban" (superseded uploads):** bank pulls are often truncated at the bottom and re-uploaded whole under the same name, leaving two overlapping Upload rows and no way to tell which one is the good copy. `Upload.superseded_by` (self-FK, `SET_NULL`, `related_name="supersedes"`) marks the older one. `_tandai_tiban` runs as the **last statement inside `_persist_rows`' `atomic()`** — so it is evaluated on *every* ingest and rolls back with a failed run — and only when the new file actually adds rows (`if objs`); a byte-identical re-upload is a no-op. **The proof is a row_hash superset:** the candidate's entire content (its own rows ∪ its `duplicate_transactions`) must be contained in the new file's hash set (`dup_tercatat | new hashes`); anything less is not marked (BCA-PDF positional hashes can legitimately fail this — fail-safe, correct). Filename matching is a **supporting** check and deliberately **asymmetric**: the incoming name is used as-is, only the *stored/candidate* name may have the Django storage suffix stripped (`_[A-Za-z0-9]{7}` before the extension) — a legacy leftover from when `original_name` came from the staging path. Stripping both sides would collapse dated exports (`MUTASI_27JUN26` and `MUTASI_28JUN26` are both 7 alnum → both become `mutasi.xlsx`), and since a cumulative day-2 bank export really does contain day 1, the superset proof would pass and day 1 would be wrongly flagged. `TIBAN_JENDELA = timedelta(days=14)` caps candidate age — a pure **engineering bound** (bounds the candidate query, limits surprise on same-name cumulative exports), *not* a client-facing rule; don't document it as one. `ingest(original_name=)` carries the uploader's real filename (sanitized `Path(v).name[:255]`); empty falls back to the staging basename, so the CLI path is unchanged. The mark is **pure metadata** — four readers, none in the engine/completeness/consume path: the Upload-history badge + tooltip, the post-commit flash (`up.supersedes.all()`), the Mutasi Bank dropdown ` · ketiban` suffix, and `_tandai_tiban`'s own `superseded_by__isnull=True` candidate gate. Transactions, attribution, and batches are never touched.

To add a new source format: write a parser subclass, register it in `PARSERS` (`services.py`), and add a detection signature in `detect.py`.

### 2. Match (`reconciliation/engine.py`) — the reconciliation logic

- **Matchers are pluggable** via the `MATCHERS` dict keyed by `MatchRun.Relation`. `PanelBracketMatcher` punya **dua mode**: mode **ticket** (join Ticket Number, kunci kuat — panel Nexus) dan mode **username** untuk panel tanpa ticket (Vigor/TM Gaming, mis. COR): kunci `(username.lower(), int(|amount|), arah dari jenis)`, penugasan global 1:1 urut selisih tanggal dalam `date_window_days`, cocok reason `username_amount`; pemilihan mode via rasio baris panel ber-ticket (`TICKET_RATIO` 0.5 inklusif), kandidat yang dua sisinya membawa ticket BERBEDA diveto (guard kontradiksi), baris bracket non-depo/wd tidak menghasilkan `no_panel`. `run_batch` memakai gerbang `panel_in_scope` + `summary["mode"]`/`skipped_detail`; dua warning (`_mode_ticket_warning`, overlap kanan-kosong) membunyikan salah-mode. Kalibrasi data riil COR 23-07-2026: 10.069/10.072 (99,97%). `_MoneyMatcher` (→ `PanelBankMatcher`, `BracketBankMatcher`) is multi-pass.
- **The anchor rule (core domain decision, do not regress):** a pair may only form on a PRIMARY anchor — exact ticket (pass 0), exact gateway `reference` e.g. QRIS UUID (pass 0b), exact rekening gateway UNO (pass 0c: `raw["AccountNumber"]` == rekening pemain di panel, HANYA nominal persis, reason `account`; rekening = kunci PEMAIN bukan transaksi, jadi sengaja TIDAK memperluas `blocked` — akun gateway yang tak dikenal panel cuma bukti celah data panel, baris uangnya tetap boleh menang lewat pass 1–3), phone/VA/account-number match or exact username or fuzzy name ≥ `fuzzy_threshold` 85 (pass 1, global score-ordered assignment, tie-broken by `_route_ok` — which reads the MIDDLE pipe segment of panel `raw["Bank Title"]` via `_expected_owner`, hence the mandatory empty middle in COR QRIS's `"QRIS||"`, see the COR bullet under Domain model conventions), near-miss on strong identity (pass 2: small fee diff — floor `FEE_TOL_MIN` 6500 (BI-Fast 2500 / online-antarbank 6500 glued into the bank debit) or 1% of amount, identity still gates: exact=100 → cocok, fuzzy → tinjau / money H-1), or name in the review band `NAME_REVIEW_FLOOR`(60)–84 → `perlu_tinjau` `name_partial` (pass 3). **Amount+date are SUPPORTING anchors only** — required (they block candidates) but never sufficient; identity < 60 means NO pair (`no_money`) so the row can wait for next-day settlement. Amount blocking uses rounded absolute value; the date window is directed (money ≥ credit date).
- Each match produces a `MatchResult` in one of three buckets: `cocok`, `tidak_cocok`, `perlu_tinjau` — plus pseudo-views in the UI: `no_panel` rows (money with no panel trace, `left=None`) are counted/displayed separately from `tidak_cocok` so `cocok+perlu_tinjau+tidak_cocok == panel row count` per run. Reason codes map to UI labels in `web/templatetags/web_extras.py` `REASON_LABELS` (keep old codes like `weak_name` there — historical rows still render).
- **Manual override (human-in-the-loop):** a reviewer can force any result's bucket regardless of what the matcher decided. `web/views.py` `review` (single result) / `bulk_review` (per-run, current filtered page) / `bulk_review_queue` (cross-run, from the "Area Pengecekan" queue `review_queue` at `/tinjau/`) set `bucket` + `reason_code="manual_override"`, write one `ReviewAction` per row (the audit trail survives independently), and **must** call `refresh_batch_summary` on every touched batch so the run/batch Cocok/Tinjau cards don't go stale against the live chips. Scope is always guarded by `tokos_for(user)`. A manual override also **consumes/locks the credit row** to the result's home batch (`_kunci_baris_override` — set `left.consumed_by_batch`): the decision is final. Without this, an override on a still-active `no_money` row (which the reason-change drops out of carry-over) leaves the row active, so the **next day's run re-processes it as a "susulan"/retro row and writes a duplicate `no_bracket`/`no_money` result that visually reverts the override** — the exact bug that hit WLG/BBS. Rows not manually reviewed stay active and can still late-settle. Every review action also carries an optional **`alasan`** (dropdown in a Koreksi-style modal, single + bulk; list **reused from `web.models.FRKoreksi` choices** — don't duplicate it) + free-text note for "Lainnya", stored on `ReviewAction` (`alasan` has no `choices=` on the model by design — validation happens in the views so the list can change without a migration; layering: `reconciliation` must not import from `web`).
- **`run_batch(toko, ...)`** is the top-level orchestrator the UI calls: checks completeness, runs the applicable relations, aggregates DP/WD totals, and — **only on success, as the last step** — "consumes" the transactions by setting `consumed_by_batch`. Consumed rows are excluded from future completeness/matching (`_active()` filters `consumed_by_batch__isnull=True`); deleting a batch frees them again (`SET_NULL`). The whole run is wrapped in `transaction.atomic()`, so a failed run rolls back completely (no orphan batch, nothing consumed).
- **Daily runs & late settlement:** the web always passes `recon_date` (one batch per `(toko, recon_date)`, guarded by view + unique constraint; redoing a date = delete the old batch first). On success, unmatched credit rows (`tidak_cocok`/`no_money`) still inside `date_window_days` are **not** consumed — they stay active "menunggu settlement". The next day's run matches them against newly-uploaded money rows; a hit **flips the original MatchResult in its home batch** (`reason_code="late_settlement"`, marked `resolved_by_batch`, home summary recomputed via `refresh_batch_summary`) and the credit row is consumed into its home batch. Carried rows never create new results in the resolving batch and are excluded from its gross totals (shown separately as "Settlement tertunda"). Unmatched carried rows past the window expire quietly into their home batch (recorded in `summary["late_settlement"]["expired"]`). Deleting a resolving batch calls `revert_late_settlements` first, restoring flips and reactivating carried/expired rows. **Retro write-back:** brand-new rows dated D < recon_date whose date already has a batch are written back to that batch (results into its runs, gross totals incremented via `_add_retro_gross`, consumed there); the current batch only notes them in `summary["retro"]`.
- The `include` dict threads through every matcher/aggregator to let a run opt specific sources in/out (panel_dp, panel_wd, bracket, bank, gateway). `include=None` means "all", the legacy behavior.

### 3. Read-only reporting views (`web/`)

Several pages aggregate existing rows **query-time — no new tables or migrations**, so they apply retroactively to production data and never touch the engine. Each has a pure aggregation module (unit-tested without rendering) called by a thin view. The one exception is the Control Bracket breakdown, which now carries a single write table, `web.models.FRKoreksi`: an overlay that corrects one cell (identified by toko/tanggal/account/kolom) without touching the underlying `Transaction` data — totals and Selisih Kontrol are recomputed from the corrected values on render, and every save/delete is logged to `AuditLog` (`fr_koreksi`/`fr_koreksi_hapus`).

- **`web/breakdown.py`** (`/bracket/`, "Control Bracket per FR Account") and **`web/rekening.py`** (`/rekening/`, per bank/gateway account) pivot straight off `Transaction.raw` via `KeyTextTransform`. Both derive per-account opening/closing balance with the **order-independent** `_saldo_batas` (in `breakdown.py`): real FR/bank rows shuffle within the same minute and backdated entries make the `Jam` stamp lie, so a positional first/last balance is wrong — instead it matches the multiset of pre-balances (`balance − delta`) against balances; a broken/non-unique chain falls back to `(Jam, id)` so the inconsistency surfaces in the **"Selisih Kontrol"** column (ideally 0) rather than being hidden. `bracket_breakdown(toko, dari, sampai=None, ...)` takes a **date range** (`sampai=dari` = the old 1-day behavior; `?date=` back-compat maps to `dari=sampai`). **Balance carry-forward:** `saldo_awal` = closing balance as of `dari−1` (`_saldo_carry`: one `Max(posted_date)` aggregate per account over rows `< dari`, then `_saldo_batas` on only those closing days — dormant balances carry with no lookback limit), movements aggregate over `[dari, sampai]`, `saldo_akhir` = closing as of `sampai`. An account with a nonzero standing balance but **no movement in range still appears** (mutasi 0, awal==akhir, Selisih Kontrol 0); once its balance is cleared to 0 (moved out / cost) it **disappears** the next day. `FRKoreksi` cell-corrections apply **only in single-day mode** (`dari==sampai`) — the correction key is a single date; range mode shows raw aggregates. `rekening_breakdown(toko, dari, sampai=None)` mirrors this range signature (`sampai=None`/`dari==sampai` = the old 1-day behavior; view keeps `?date=` back-compat, filter bar `Dari`/`Sampai` uniform with Rincian Biaya, default = latest single day). It has **no dormant carry-forward** — money rows are keyed on the Python property `source_label_full` (not a DB column groupable like FR's `raw["Bank"]`), and an account only appears when it has in-range movement; `saldo_awal`/`saldo_akhir` come from `_saldo_batas` over in-range rows (carry-in is automatic for a continuous chain since the first row's pre-balance = the prior day's close). Over a **multi-day range with a broken chain**, `_saldo_batas`'s endpoints can be non-chronological (same limitation as `bracket_breakdown`) — Selisih Kontrol ≠ 0 flags it; the single-day default sidesteps it.
- **`web/hutang.py`** (`/hutang-piutang/`) lists bracket rows whose `Kategori` is Hutang/Piutang, across dates, with running totals — same query-time pattern, no overlay.
- **`web/biaya.py`** (`/biaya-admin/`, "Rincian Biaya") rolls up bank fee rows per channel (E-wallet/BI Fast/Transfer online) — rows tagged `jenis="admin"` plus legacy rows matched query-time via `is_admin_fee`, grouped by date + `source_label_full`.
- **`web/bonus.py`** (`/bonus/`, "Rekonsiliasi Bonus") matches panel bonus rows against bracket bonus rows query-time — key = username (lowercase, brand prefix stripped) + rounded amount + date, greedy 1:1 per key → buckets cocok/panel_only/bracket_only + per-kategori summary. Feeds off two dedicated SourceTypes `panel_bonus`/`bracket_bonus` (parsers in `sources/parsers/bonus.py`; panel "Credit Balance" export takes ONLY bonus-prefixed Description rows and skips the net-zero `Offset` twins; bracket "Non Credit Bonus" maps code **K-BLD → "Lucky Draw"**; panel `Amt.` is ×1000, bracket `Nominal` is full rupiah). These keys are invisible to `check_completeness`/matchers/consume — the bonus path can never disturb the daily DP/WD pipeline. Display adds a query-time **kategori detail** (promo name extracted from the panel Description, e.g. "BONUS ROLLINGAN SLOT 0.5% DAILY"; bracket rows keep their mapped kategori — the two namespaces stay separate, so a cross-name pair shows as two summary rows) + a `?kategori=` filter and per-kategori value columns; none of it changes pairing (filter applies to the already-paired result).
- **`web/channels.py`** (dashboard "Metode Pembayaran" card) classifies the last batch's consumed panel rows by their raw panel **Bank Title** (client rule: contains "QR" → QRIS — including "NXPAY DEPOSIT QR"; DP order QR → e-wallet → Bank; WD order Nexuspay → QR → Bank; empty/unknown → "Lainnya", hidden at 0). Uses the same queryset as the dashboard's `panel_sum` so breakdown totals always equal the summary strip.
- **`web/rekap.py`** (`/rekap-bulanan/`, "Rekap Bulanan") meniru rekap Excel bulanan klien: 4 seksi (Net Profit / Sisa Dana Member / Total Dana Lebih Web / Selisih + penyebab) dari registry `FIELDS` (slug, seksi, kind manual/auto/carry/computed, arah tanda — SEMUA rumus hidup di modul ini, template tanpa aritmetika). Angka auto = 1 query per sumber (bonus per kategori dgn catch-all `bonus_lain` + tes konservasi, kategori FR, DP/WD dari sum `Transaction` panel langsung, hutang/piutang); carry rekursif depth-1 dari bulan sebelumnya; isian manual `RekapManual` (unik toko+periode+field, migrasi web 0002; field TANPA `choices=` by design — validasi di view) menimpa auto dengan provenance; penyebab selisih = `RekapPenyebab`; edit lewat popup HTMX pola `fr_koreksi` + OOB refresh banner kunci; param `?bulan=YYYY-MM`. Kartu dashboard **"Ringkasan Bracket"** = `ringkas_bracket_hari(toko, tanggal)` di `breakdown.py` (grouped query + overlay FRKoreksi skip-absent, tie-out persis dgn `bracket_breakdown` — dijaga tes).
- **Dashboard filter tanggal (`?dari=&sampai=`, `web/views.py` `dashboard`)**: tanpa parameter = perilaku lama (potret batch TERAKHIR) — itu kontrak yang dijaga tes. Dengan parameter, `_filter_rentang` (ladder resolusi sama dgn `/bracket/` & `/rekening/`: satu sisi kosong = 1 hari, terbalik ditukar, tanggal ngawur diabaikan) menyalakan mode jendela: `panel_sum`/`metode` = agregat `consumed_by_batch_id__in` SEMUA batch in-range, selisih & Uang periksa (D) dijumlah, tren = batch jendela, kalender ber-anchor `sampai`, runs difilter `batch__recon_date`. Kartu Bracket memakai `ringkas_bracket_rentang` (breakdown.py) yang mendelegasi ke `ringkas_bracket_hari` saat 1 hari dan meng-abs withdraw **per akun** saat rentang — supaya tie out dengan `bracket_breakdown(dari, sampai)["total"]`; overlay `FRKoreksi` ikut aturan halaman /bracket/ (hanya 1 hari). Panel **"Kerjakan hari ini" sengaja TIDAK ikut jendela** (`live_last`/`um_d_live` = batch terakhir toko): daftar kerja harus tetap hidup, kalau tidak badge jendela berdampingan dengan tombol yang cuma membuka satu batch. Mode "Semua Toko" menerima filter yang sama lewat `_dashboard_semua(request, dari, sampai)`; bracket-nya lewat `_ringkas_bracket_gabungan(toko_ids=…, rentang=…)`, dan jumlah query WAJIB tetap konstan terhadap jumlah toko di KEDUA mode (dijaga dua tes N+1).
- **`web/penjaga.py`** — three post-ingest **warnings** (never blockers) flashed by the upload-commit handler: content dates far from the date in the filename, row count far from that **stream's** habit in that toko (median of the last 10 uploads whose `kunci_aliran` matches, using `rows_parsed + rows_duplicate` = the file's real size). **The habit pool must be per-stream, not per `source_type`+`flow`** — that was v1.14.0's bug: on Vigor/TM Gaming one `panel`+`dp` bucket holds both `PANEL DP SLO` (±140 rows, pairs with the bank) and `PANEL QRIS DP SLO` (±6.900 rows, pairs with the QRIS file), and bank files pool across accounts. The mixed pool is bimodal and its median lands in the empty valley between the modes (real SLO data 03-08-2026: median 2.670), and it *shifts with upload order within one submission* — the bank-panel file was judged against 2.670 and the QRIS file a second later against 147, producing three false positives on the first real day. `kunci_aliran(nama)` derives stream identity from the uploader's own naming: strip date + extensions (including doubled `.xlsx.xlsx`), then take the **set** of remaining word tokens — a set, not a sequence, because W25 renamed `QRIS UNOPAY DP W25` → `W25 DP QRIS UNOPAY` and that must stay one stream. `flow` deliberately does NOT filter the pool (direction is already in the name; a misdetected flow would split a stream for no reason), and — gateway only — the upload's transaction keys having ~no overlap with the panel's for those dates. Real cases: a file named `01-08-2026` holding 30/06–01/07 rows (dragged SLO's panel-range floor back a month, tripping the panel-anchor gate over all of July), and a 9.156-row UNOPAY file in a toko whose habit is 615–714 whose keys matched the panel **0%** (→ 9.618 `no_panel` rows in one batch). **Warn-only is a decision, not laziness:** all three infer from habit, and habit doesn't exist for a new brand/merchant — a miscalibrated blocker would stop a toko from working until the code is fixed. Each check goes **silent when evidence is thin** (<5 prior uploads, empty comparison panel, <20 keys); a guard that cries wolf gets ignored. The checkers are **pure** (numbers/sets, not querysets) so thresholds are testable without a DB; only `periksa_upload` touches the DB and it **swallows its own exceptions** — it is called inside the commit handler's `try`, so an exception there would report a *successful* upload as failed. The panel side is read **regardless of consume status** (the panel for that date is usually already consumed) and unions `reference` + `ticket_no` (superset ⇒ fewer false accusations).
- **`web/kelengkapan.py`** `status_sumber(toko, dari, sampai)` — per-source `aktif`/`terpakai`/`batch_no`/`batch_tanggal` for the Kelengkapan Data card, **3 queries regardless of source count** (guarded by a test). Deliberately separate from the engine's `check_completeness`: that one returns booleans that get persisted into `ReconBatch.completeness`, so its shape is a contract display must not alter. It exists because "no active rows" hid three very different situations behind one grey "opsional" pill — a W25 user concluded the UNOPAY gateway was unreadable while 9.586 of its rows were already consumed by Batch #27.
- **`web/monthly.py`** (`/bulanan/`) reads `ReconBatch.summary` as-is per day (use `money`/matched, **not** `money_gross` — gross can dwarf panel). **`web/settlement.py`** (`/settlement/`) lists still-waiting credit rows via the engine's `_carried_results`. **`web/exports.py`** builds the Excel workbooks for the Export page and per-run export — `build_batch_workbook` now also appends **Breakdown Bracket** + **Rincian Rekening** sheets (old Ringkasan/Hasil sheets unchanged), and `/bracket/export/` (`export_breakdown` view) exports the breakdown table honoring the active date range + carried balances.

**Client-facing UX (global, no per-page code):** two vanilla-JS modules are loaded once in `app_base.html`, both dependency-free and build-step-free. `web/static/web/js/range-select.js` gives every `table.selectable` **Excel-style rectangular cell selection** — drag a block (e.g. cols 3–4 only, never sweeping adjacent columns), Cmd/Ctrl+C copies it as TSV (tabs between columns, newlines between rows) ready to paste into a spreadsheet. It bails on interactive targets (links, the FRKoreksi correction cells, inputs) so normal clicks and text-copy still work. Add the feature to a table by putting `class="selectable"` on it. `web/static/web/js/toko-picker.js` progressively enhances the Toko picker (top bar + the Pengingat Toko modal) into a searchable combobox — a trigger button plus a popover with a search box and a filtered `role="listbox"`, because 16+ brands with short similar names (MUL MXW M25 K25) are miserable to scroll. **Binding invariant:** the server-rendered `<select name="toko_id">` markup in `app_base.html` must not change by a single byte (older tests pin the exact strings), the native select stays the source of truth (selecting sets `select.value` then submits the form, exactly like its own `onchange="this.form.submit()"`), and it is hidden (class `.tp-native`) **only after the control builds successfully** — if anything throws, the plain picker is still there and still works. The login page (`registration/login.html`) rotates a random professional tagline (`login_tagline`, chosen server-side in `AuditorLoginView`) on every GET — the kinetic `<h1>` hero is untouched.

## Domain model conventions (critical, easy to get wrong)

All money is normalized to **rupiah** on the canonical `Transaction`. Sign and scale conventions:

- **`credit_delta`** = effect on the operator's credit ledger; **`money_delta`** = effect on real cash. A deposit is `money_delta > 0` / `credit_delta < 0`; a withdrawal is the reverse. Matching requires the two sides to share the same money direction.
- **Panel amounts are in thousands** — the panel parser multiplies by `SCALE = 1000` to reach rupiah. Don't double-apply. **Exception: COR (Gacor25) exports are already in full rupiah** — the `cor_*` parsers must NOT ×1000. COR QRIS **panel** rows have no destination-bank column, so the parser synthesizes `raw["Bank Title"] = "QRIS||"` (column `bank_title = "QRIS"`); `sources/management/commands/backfill_qris_bank_title.py` fills the same pair on rows ingested before that (structurally gated to Vigor/TM-Gaming tokos — the `"QRIS "`-description selector alone would also sweep free-text Nexus Remarks). **The empty middle segment is an engine invariant, not cosmetics — do NOT "tidy" it to a bare `"QRIS"`.** `reconciliation/engine.py` `_expected_owner` returns the middle pipe segment and falls back to the *whole string* when there is no `|`, so `"QRIS"` would hand the matcher a rail label where it expects an account-owner name, switching `_route_ok` on for the entire COR QRIS population (it is a secondary sort key in pass 1's greedy 1:1 assignment — silently different pairings, no error anywhere).
- **Per-brand exact keys on the money side** (prefer these over fuzzy): COR QRIS `Transaction ID` (UUID) == gateway `OrderId` → `reference`; MUL QRIS-HOKI `Whitelabel Transaction ID` == panel ticket; MXW QRFlyer `TXN ID` / NXPay `Ticket Number` == panel ticket; UNO QRIS-WD `Order ID (Merchant)` (UUID penuh) == panel Vigor/TMG WD `Transaction ID` (parser `cor_qris_wd_gateway`, REFUND rows dilewati). RPay (MUL/M77) sengaja TANPA `reference` — anchor = `Customer Username` == username panel; UUID hanya di `raw` karena Remarks panel Nexus terbukti tidak memuatnya (aturan blocked engine akan mengasingkan reference tak dikenal panel). BBS RafflesPay varian XLSX: DP `rpay_xlsx` (`Ticket Number` D... == panel; RRN hanya di raw, ada duplikat nyata) dan WD `rpay_wd_xlsx` (header dua-tingkat, `Ticket` W... == panel, hanya `Transfer=success`, `Disbursed Amount` = uang keluar). Some COR exports lack the xlsx `<dimension>` tag and have broken stylesheets — read them with the styles-tolerant raw reader in `sources/parsers/base.py`, not plain openpyxl.
- **Fee rows are tagged `jenis="admin"`** and deliberately excluded from WD money totals, matching, and completeness (they aren't real withdrawals): BCA `BIAYA TXN` rows, and BRI **BRIVA** fee rows (each BRIVA e-wallet WD pairs with an identical-description Rp1.000 debit twin, `is_briva_fee`). BRI `ATMSTRPRM…`@6500 / `BFST…`@2500 / `BRIVA…`@1000 and Mandiri `Biaya…` are now flagged via `sources/parsers/fee_rules.is_admin_fee` (used both by the parsers at ingest and, query-time, by the Rincian Biaya report for legacy rows ingested before the rule existed).
- **WD e-wallet via BRI (BRIVA)**: mutasi shows `BRIVA<channel code><phone>` glued together (DANA 88810, GOPAY 30135, OVO 88099, SHOPEEPAY 112, LINK AJA 91188) — the 16-18 digit run defeats the generic 9-15 digit phone scan, so `_money_phones` has a dedicated `_BRIVA_RE` that strips the code before phone matching. Client's channel-trace matrix ("TRANSAKSI KELUAR MUTASI WITHDRAW") is the source of truth for which bank→channel combos carry identity at all (e.g. BNI→GOPAY carries NO number — unmatchable by identity).
- Match keys on `Transaction`: `ticket_no` (panel `D…`/`W…`), `reference` (gateway), `username`, `counterparty` (bank sender/receiver name). Names are isolated per-source in the parser; the engine only normalizes + fuzzy-matches.
- `USE_TZ = False` — bank/panel timestamps are naive local (WIB, `Asia/Jakarta`). Don't introduce tz-aware datetimes.

## Access control (`web/access.py`)

RBAC is scoped **per Toko** (brand/site). `tokos_for(user)` is the single source of truth: admins/supervisors see all active Tokos; auditors see only `allowed_tokos`. The custom user model is `accounts.User` (roles: admin/supervisor/auditor; no public signup). The active Toko lives in the session (`active_toko_id`) and is injected into every template by the `web.context_processors.toko` context processor. **Mode "Semua Toko" (khusus admin):** session boleh berisi sentinel `"all"` — `_active_toko` WAJIB tetap mengembalikan objek Toko nyata (guard mengembalikan toko pertama yang diizinkan; jangan pernah biarkan `"all"` menyentuh query — `filter(id="all")` crash di Postgres), context processor men-set flag `semua_toko` (via `web.access.mode_semua`), dashboard beralih ke template terpisah `dashboard_all.html` (agregat lintas toko TANPA loop query per-toko — dijaga tes assertNumQueries konstan), Hutang/Piutang menerima ceklis multi-toko `?toko=` (kosong = semua, disaring `tokos_for`), dan halaman lain menampilkan bar penjelas — `semua_toko_page=True` menandai view yang sudah sadar-mode (bar hilang), `semua_toko_tulis=True` memakai varian peringatan di halaman tulis (upload/rekonsiliasi/rekap/bracket). `Toko.panel` (nexus/vigor/tm_gaming, wajib saat membuat toko) mengelompokkan kedua picker via `tokos_grouped` (optgroup, 0 query ekstra). Web views live in `web/views.py` (reconciliation flow) and `web/admin_views.py` (Toko/user management, deletes).

`web/middleware.py` `ForcePasswordChangeMiddleware` (registered right after `AuthenticationMiddleware`) gates **every** request for users flagged `must_change_password` → redirected to `/ganti-password/` until they change it (admins set the flag when creating a user or resetting someone else's password). `IPAllowlistMiddleware` (urutan rantai: Auth → GeoBlock → ForcePassword → **IPAllowlist**, dipin tes) menggembok **auditor & supervisor** ke daftar `web.models.AllowedIP` (CRUD `/kelola/ip/`, admin-only, CIDR dinormalisasi `ip_network(strict=False)`): dorman selama daftar aktif kosong, admin/superuser tidak pernah digerbang, IP internal/loopback lolos, query gagal = fail-open BERSUARA di log, penolakan → 403 `ip_block.html` + `catat("ip_blokir")` sekali per sesi per IP. Sensitive admin/account actions are written to `core.models.AuditLog` via `core.audit.catat`, which snapshots the actor's username so the trail survives a later user deletion (`/kelola/log/`, admin-only).

## Versioning

`core/version.py` is the **single source of truth**: a `RILIS` tuple of `Rilis` dataclasses, newest first, whose top entry defines the running version. It feeds the sidebar/login badge (`core.context_processors.versi` → `app_versi`/`app_rilis`), the `/versi/` Riwayat Versi page, the `Versi aplikasi` row stamped into every exported workbook's Ringkasan sheet, and `CHANGELOG.md`.

**Shipping a user-visible change means adding a release entry** — prepend a `Rilis(...)`, run `python manage.py changelog`, commit both. `core/tests_version.py` fails the suite if `CHANGELOG.md` drifts, if the ordering/date sequence breaks, or if a release's declared `jenis` doesn't match its number jump (mayor→X+1.0.0, minor→x.Y+1.0, patch→x.y.Z+1).

Scheme (spelled out in the module docstring, including the explicit 2.0.0 criteria): MAYOR = the way the app works changes fundamentally; MINOR = a new capability worth announcing; PATCH = pure fixes; 0.x = pre-production. **New banks/gateways/brands, new report pages, and tighter access control stay MINOR no matter how many** — that rule is what keeps the numbering meaningful.

Release boundaries are drawn on **contiguous commit ranges** (one release = one whole date window, never interleaved), which is what makes the retroactive 0.1.0–1.9.0 map verifiable: the 15 commit-bearing releases tile all 281 commits exactly, no gaps, no overlaps. Preserve that property when adding entries. Business-language summary for management: `docs/ringkasan-versi-2026-07-25.md`.

- **Git flow:** commit per work chunk AND push to `origin/main` (fast-forward only, never force). A teammate (`sabian`) also lands on main — always `git fetch` + rebase before pushing.

- **Geo-block (K4) is LIVE in prod (2026-07-22): KH-only.** `web/middleware.GeoBlockMiddleware` + `geoip2fast` (bundled country DB, no key/network). Controlled entirely by Railway env vars (code default is OFF): `GEO_BLOCK_ENABLED=true`, `GEO_BLOCK_COUNTRIES=KH` (allow-list of ISO codes), `GEO_BLOCK_BYPASS_STAFF=true`, optional `GEO_BLOCK_ALLOWLIST` (IP/CIDR break-glass). Bungkus anotasinya `Cast(KeyTextTransform(...), TextField())` — lihat `web/views.py` `_chips_sumber_uang`, yang mengisi chip "Filter bank/sumber" tab **Tidak Ada di Panel** untuk `run_detail` + `review_queue`: baris uang bank/gateway dilabeli dari upload (`specific_source_label`), baris **FR/Bracket** dari `raw["Bank"]` — karena `specific_source_label` sengaja mengembalikan "Bracket" generik untuk panel/bracket, dan chip satu-pilihan itu percuma (keluhan klien 2026-07-27, relasi panel_bracket panel Vigor/TM Gaming).
- Django 5.2 keeps the cached template loader on even in DEBUG — restart the dev server after editing templates before concluding an edit "didn't work".
- Django `{# #}` comments are **single-line only** — a multi-line one leaks into the rendered page (twice now; the Paket I leak contained the literal word `<template>`, which became a real tag and swallowed the entire body while the test suite stayed green).
