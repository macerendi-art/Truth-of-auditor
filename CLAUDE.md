# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Truth of Auditor** — a Django 5.2 app that reconciles a betting/credit operator's records across four kinds of sources: the **Panel** (site's own DP/WD history), the **Bracket** (agent ledger), **Banks**, and payment **Gateways**. It ingests exported files (xlsx/csv/pdf, some encrypted), normalizes every row into one canonical `Transaction`, then matches credit-side records against money-side records to surface discrepancies. UI and code comments are in Indonesian; keep that convention.

## Commands

The virtualenv is at `.venv`. Activate it first: `source .venv/bin/activate`.

```bash
python manage.py test                         # run all tests (~850)
python manage.py test web.tests_reconcile     # one module
python manage.py test web.tests_reconcile.SomeTestCase.test_x   # one test
python manage.py runserver                     # dev server (sqlite, DEBUG=True)
python manage.py migrate                        # apply migrations (includes seed data)

# CLI equivalents of the core pipeline (useful for debugging without the UI):
python manage.py ingest <parser_key> <file_path> [--flow dp|wd] [--password ...]
python manage.py match <panel_bracket|panel_bank|bracket_bank> [--from YYYY-MM-DD] [--to YYYY-MM-DD]

# Fase-0 harness: ingest a folder of real exports + auto daily batches + match-rate report.
# Use this to calibrate matcher changes against real data BEFORE shipping.
python manage.py validate_brands --dir <folder> --toko <mul|g25|mxw|...> --flow-from-name
```

Reference data (SourceTypes, the "Default" ToleranceProfile, seeded Tokos) is created by **data migrations**, not fixtures — a fresh `migrate` gives you a working DB. Tests rely on these seeds existing.

To run anything against a throwaway DB (calibration, repros) without touching the dev DB, point `DATABASE_URL` at a scratch sqlite file: `DATABASE_URL=sqlite:////tmp/scratch.sqlite3 python manage.py migrate && ... validate_brands ...`.

## Architecture: the ingest → match pipeline

Everything flows through two stages. Understanding these two modules explains most of the codebase.

### 1. Ingest (`sources/`) — heterogeneous files → canonical `Transaction`

- **`sources/detect.py`** `detect_source(path, filename)` sniffs header tokens / extension and returns ranked `{parser_key, confidence}`. The web upload flow auto-detects, and only asks the user to confirm when confidence < 0.8.
- **`sources/services.py`** `ingest(parser_key, file_path, ...)` is the single entry point: picks the parser from the `PARSERS` dict, decrypts first if the file is an encrypted xlsx (OLE2 magic bytes → `msoffcrypto`, Mandiri e-statements), runs it, and bulk-creates `Transaction` rows inside one atomic block.
- **`sources/parsers/`** one class per format (`panel`, `bracket`, `banks.py` → BRI/BCA-CSV/Mandiri, `bca_pdf` + `bni_pdf` → bank e-statement PDFs (both emit `source_key="bank"`), `gateways.py` → NXPay/QRFlyer/RPay/QHoki, `cor.py` → COR/Gacor25 panel-bank/QRIS/QRIS-WD, `bonus.py` → panel_bonus/bracket_bonus). Each subclasses `BaseParser` and returns a list of dicts whose keys **exactly match `Transaction` fields**. Shared parsing helpers (decimal/date parsing for both `intl` and `id` number formats, ticket/ref regexes, `clean_name`, `row_hash`, the styles-tolerant `read_xlsx_rows`) live in **`sources/parsers/base.py`**.
- **Idempotency:** every row gets a `row_hash` (stable hash of key fields). `ingest` skips hashes that already exist for that `(source_type, toko)`, so re-importing the same file is safe. Skipped rows are additionally **linked** to the new upload via `Upload.duplicate_transactions` (M2M) — bank exports are often rolling/overlapping, and this link is what lets the Mutasi Bank per-file filter reconstruct the file's full content (uploads from before the field exist without links and fall back to attributed-rows-only).
- **"Ketiban" (superseded uploads):** bank pulls are often truncated at the bottom and re-uploaded whole under the same name, leaving two overlapping Upload rows and no way to tell which one is the good copy. `Upload.superseded_by` (self-FK, `SET_NULL`, `related_name="supersedes"`) marks the older one. `_tandai_tiban` runs as the **last statement inside `_persist_rows`' `atomic()`** — so it is evaluated on *every* ingest and rolls back with a failed run — and only when the new file actually adds rows (`if objs`); a byte-identical re-upload is a no-op. **The proof is a row_hash superset:** the candidate's entire content (its own rows ∪ its `duplicate_transactions`) must be contained in the new file's hash set (`dup_tercatat | new hashes`); anything less is not marked (BCA-PDF positional hashes can legitimately fail this — fail-safe, correct). Filename matching is a **supporting** check and deliberately **asymmetric**: the incoming name is used as-is, only the *stored/candidate* name may have the Django storage suffix stripped (`_[A-Za-z0-9]{7}` before the extension) — a legacy leftover from when `original_name` came from the staging path. Stripping both sides would collapse dated exports (`MUTASI_27JUN26` and `MUTASI_28JUN26` are both 7 alnum → both become `mutasi.xlsx`), and since a cumulative day-2 bank export really does contain day 1, the superset proof would pass and day 1 would be wrongly flagged. `TIBAN_JENDELA = timedelta(days=14)` caps candidate age — a pure **engineering bound** (bounds the candidate query, limits surprise on same-name cumulative exports), *not* a client-facing rule; don't document it as one. `ingest(original_name=)` carries the uploader's real filename (sanitized `Path(v).name[:255]`); empty falls back to the staging basename, so the CLI path is unchanged. The mark is **pure metadata** — four readers, none in the engine/completeness/consume path: the Upload-history badge + tooltip, the post-commit flash (`up.supersedes.all()`), the Mutasi Bank dropdown ` · ketiban` suffix, and `_tandai_tiban`'s own `superseded_by__isnull=True` candidate gate. Transactions, attribution, and batches are never touched.

To add a new source format: write a parser subclass, register it in `PARSERS` (`services.py`), and add a detection signature in `detect.py`.

### 2. Match (`reconciliation/engine.py`) — the reconciliation logic

- **Matchers are pluggable** via the `MATCHERS` dict keyed by `MatchRun.Relation`. `PanelBracketMatcher` punya **dua mode**: mode **ticket** (join Ticket Number, kunci kuat — panel Nexus) dan mode **username** untuk panel tanpa ticket (Vigor/TM Gaming, mis. COR): kunci `(username.lower(), int(|amount|), arah dari jenis)`, penugasan global 1:1 urut selisih tanggal dalam `date_window_days`, cocok reason `username_amount`; pemilihan mode via rasio baris panel ber-ticket (`TICKET_RATIO` 0.5 inklusif), kandidat yang dua sisinya membawa ticket BERBEDA diveto (guard kontradiksi), baris bracket non-depo/wd tidak menghasilkan `no_panel`. `run_batch` memakai gerbang `panel_in_scope` + `summary["mode"]`/`skipped_detail`; dua warning (`_mode_ticket_warning`, overlap kanan-kosong) membunyikan salah-mode. Kalibrasi data riil COR 23-07-2026: 10.069/10.072 (99,97%). `_MoneyMatcher` (→ `PanelBankMatcher`, `BracketBankMatcher`) is multi-pass.
- **The anchor rule (core domain decision, do not regress):** a pair may only form on a PRIMARY anchor — exact ticket (pass 0), exact gateway `reference` e.g. QRIS UUID (pass 0b), exact rekening gateway UNO (pass 0c: `raw["AccountNumber"]` == rekening pemain di panel, HANYA nominal persis, reason `account`; rekening = kunci PEMAIN bukan transaksi, jadi sengaja TIDAK memperluas `blocked` — akun gateway yang tak dikenal panel cuma bukti celah data panel, baris uangnya tetap boleh menang lewat pass 1–3), phone/VA/account-number match or exact username or fuzzy name ≥ `fuzzy_threshold` 85 (pass 1, global score-ordered assignment, tie-broken by `_route_ok` — which reads the MIDDLE pipe segment of panel `raw["Bank Title"]` via `_expected_owner`, hence the mandatory empty middle in COR QRIS's `"QRIS||"`, see the COR bullet under Domain model conventions), near-miss on strong identity (pass 2: small fee diff — floor `FEE_TOL_MIN` 6500 (BI-Fast 2500 / online-antarbank 6500 glued into the bank debit) or 1% of amount, identity still gates: exact=100 → cocok, fuzzy → tinjau / money H-1), or name in the review band `NAME_REVIEW_FLOOR`(60)–84 → `perlu_tinjau` `name_partial` (pass 3). **Amount+date are SUPPORTING anchors only** — required (they block candidates) but never sufficient; identity < 60 means NO pair (`no_money`) so the row can wait for next-day settlement. Amount blocking uses rounded absolute value; the date window is directed (money ≥ credit date).
- Each match produces a `MatchResult` in one of three buckets: `cocok`, `tidak_cocok`, `perlu_tinjau` — plus pseudo-views in the UI: `no_panel` rows (money with no panel trace, `left=None`) are counted/displayed separately from `tidak_cocok` so `cocok+perlu_tinjau+tidak_cocok == panel row count` per run. Reason codes map to UI labels in `web/templatetags/web_extras.py` `REASON_LABELS` (keep old codes like `weak_name` there — historical rows still render).
- **Manual override (human-in-the-loop):** a reviewer can force any result's bucket regardless of what the matcher decided. `web/views.py` `review` (single result) / `bulk_review` (per-run, current filtered page) / `bulk_review_queue` (cross-run, from the "Area Pengecekan" queue `review_queue` at `/tinjau/`) set `bucket` + `reason_code="manual_override"`, write one `ReviewAction` per row (the audit trail survives independently), and **must** call `refresh_batch_summary` on every touched batch so the run/batch Cocok/Tinjau cards don't go stale against the live chips. Scope is always guarded by `tokos_for(user)`. A manual override also **consumes/locks the credit row** to the result's home batch (`_kunci_baris_override` — set `left.consumed_by_batch`): the decision is final. Without this, an override on a still-active `no_money` row (which the reason-change drops out of carry-over) leaves the row active, so the **next day's run re-processes it as a "susulan"/retro row and writes a duplicate `no_bracket`/`no_money` result that visually reverts the override** — the exact bug that hit WLG/BBS. Rows not manually reviewed stay active and can still late-settle. Every review action also carries an optional **`alasan`** (dropdown in a Koreksi-style modal, single + bulk; list **reused from `web.models.FRKoreksi` choices** — don't duplicate it) + free-text note for "Lainnya", stored on `ReviewAction` (`alasan` has no `choices=` on the model by design — validation happens in the views so the list can change without a migration; layering: `reconciliation` must not import from `web`).
- **`run_batch(toko, ...)`** is the top-level orchestrator the UI calls: checks completeness, runs the applicable relations, aggregates DP/WD totals, and — **only on success, as the last step** — "consumes" the transactions by setting `consumed_by_batch`. Consumed rows are excluded from future completeness/matching (`_active()` filters `consumed_by_batch__isnull=True`); deleting a batch frees them again (`SET_NULL`). The whole run is wrapped in `transaction.atomic()`, so a failed run rolls back completely (no orphan batch, nothing consumed).
- **Daily runs & late settlement:** the web always passes `recon_date` (one batch per `(toko, recon_date)`, guarded by view + unique constraint; redoing a date = delete the old batch first). On success, unmatched credit rows (`tidak_cocok`/`no_money`) still inside `date_window_days` are **not** consumed — they stay active "menunggu settlement". The next day's run matches them against newly-uploaded money rows; a hit **flips the original MatchResult in its home batch** (`reason_code="late_settlement"`, marked `resolved_by_batch`, home summary recomputed via `refresh_batch_summary`) and the credit row is consumed into its home batch. Carried rows never create new results in the resolving batch and are excluded from its gross totals (shown separately as "Settlement tertunda"). Unmatched carried rows past the window expire quietly into their home batch (recorded in `summary["late_settlement"]["expired"]`). Deleting a resolving batch calls `revert_late_settlements` first, restoring flips and reactivating carried/expired rows. **Retro write-back:** brand-new rows dated D < recon_date whose date already has a batch are written back to that batch (results into its runs, gross totals incremented via `_add_retro_gross`, consumed there); the current batch only notes them in `summary["retro"]`.
- The `include` dict threads through every matcher/aggregator to let a run opt specific sources in/out (panel_dp, panel_wd, bracket, bank, gateway). `include=None` means "all", the legacy behavior.

### 3. Read-only reporting views (`web/`)

Several pages aggregate existing rows **query-time — no new tables or migrations**, so they apply retroactively to production data and never touch the engine. Each has a pure aggregation module (unit-tested without rendering) called by a thin view. The one exception is the Control Bracket breakdown, which now carries a single write table, `web.models.FRKoreksi`: an overlay that corrects one cell (identified by toko/tanggal/account/kolom) without touching the underlying `Transaction` data — totals and Selisih Kontrol are recomputed from the corrected values on render, and every save/delete is logged to `AuditLog` (`fr_koreksi`/`fr_koreksi_hapus`).

- **`web/breakdown.py`** (`/bracket/`, "Control Bracket per FR Account") and **`web/rekening.py`** (`/rekening/`, per bank/gateway account) pivot straight off `Transaction.raw` via `KeyTextTransform`. Both derive per-account opening/closing balance with the **order-independent** `_saldo_batas` (in `breakdown.py`): real FR/bank rows shuffle within the same minute and backdated entries make the `Jam` stamp lie, so a positional first/last balance is wrong — instead it matches the multiset of pre-balances (`balance − delta`) against balances; a broken/non-unique chain falls back to `(Jam, id)` so the inconsistency surfaces in the **"Selisih Kontrol"** column (ideally 0) rather than being hidden. `bracket_breakdown(toko, dari, sampai=None, ...)` takes a **date range** (`sampai=dari` = the old 1-day behavior; `?date=` back-compat maps to `dari=sampai`). **Balance carry-forward:** `saldo_awal` = closing balance as of `dari−1` (`_saldo_carry`: one `Max(posted_date)` aggregate per account over rows `< dari`, then `_saldo_batas` on only those closing days — dormant balances carry with no lookback limit), movements aggregate over `[dari, sampai]`, `saldo_akhir` = closing as of `sampai`. An account with a nonzero standing balance but **no movement in range still appears** (mutasi 0, awal==akhir, Selisih Kontrol 0); once its balance is cleared to 0 (moved out / cost) it **disappears** the next day. `FRKoreksi` cell-corrections apply **only in single-day mode** (`dari==sampai`) — the correction key is a single date; range mode shows raw aggregates. `rekening_breakdown(toko, dari, sampai=None)` mirrors this range signature (`sampai=None`/`dari==sampai` = the old 1-day behavior; view keeps `?date=` back-compat, filter bar `Dari`/`Sampai` uniform with Rincian Biaya, default = latest single day). It has **no dormant carry-forward** — money rows are keyed on the Python property `source_label_full` (not a DB column groupable like FR's `raw["Bank"]`), and an account only appears when it has in-range movement; `saldo_awal`/`saldo_akhir` come from `_saldo_batas` over in-range rows (carry-in is automatic for a continuous chain since the first row's pre-balance = the prior day's close). Over a **multi-day range with a broken chain**, `_saldo_batas`'s endpoints can be non-chronological (same limitation as `bracket_breakdown`) — Selisih Kontrol ≠ 0 flags it; the single-day default sidesteps it.
- **`web/detail_fr.py`** (`/bracket/detail/`, "Detail FR/Bracket") — the rows behind each Control Bracket cell ("that Adjustment of 450.000 — which three rows?"). **Its whole value is that it sums back exactly to the breakdown cell**, so it mirrors `bracket_breakdown`'s unusual queryset verbatim: `posted_date__range` (not `occurred_at`), and **no** `is_duplicate=False`, **no** `.exclude(jenis="admin")`, **no** consume filter — the three filters that are reflexive elsewhere in this codebase and would silently shrink the total here. It **imports** `_norm_akun`/`_slug_kategori`/`KATEGORI_KANONIK` from `breakdown.py` and filters in **Python**, never SQL: the cell keys are those Python normalizations (`Withdraw`→`withdrawal`, account names stripped), so a DB equality on `raw["Kategori"]` loses variant spellings — and `KeyTextTransform` in WHERE would need `Cast` anyway. Note `_norm_akun` strips only *edge* whitespace, so a doubled inner space really is a separate account in **both** modules; a test pins that equivalence so nobody "tidies" one side alone. `FRKoreksi` is reported, not applied: a corrected cell legitimately differs from its raw rows, and the page says so (single-day only, same as `/bracket/`). Tie-out is guarded by a test that walks **every** (account, category) cell, plus a real-data check (G25 05-08-2026: 45 cells, 0 mismatches, 10.984 rows). Breakdown's own cells stay click-to-correct — the shortcut lives INSIDE the `FRKoreksi` panel that already opens on that click ("Lihat N baris penyusunnya →", built in `fr_koreksi_form`), not as a chooser menu before it: correcting is daily work and must stay one click, while reading detail is occasional. `saldo_awal`/`saldo_akhir` deliberately get no link — they are balance positions, not sums of any rows, so pointing them at a row list would mislead. **Facet counts are cross-filtered**: each chip's number counts rows passing every *other* active filter but ignoring its own dimension, so the invariant "the number on a chip equals the rows you get by clicking it" always holds (v1.16.0 shipped globally-counted chips — "Beban Admin Bank 95" led to 2 rows once an account was picked; a property test now walks every chip under several filter combinations). Zero-count chips are hidden (they only lead to an empty page), except the currently selected one, which is always kept so the UI never loses its own selection.
- **`web/hutang.py`** (`/hutang-piutang/`) lists bracket rows whose `Kategori` is Hutang/Piutang, across dates, with running totals — same query-time pattern, no overlay.
- **`web/biaya.py`** (`/biaya-admin/`, "Rincian Biaya") rolls up bank fee rows per channel (E-wallet/BI Fast/Transfer online) — rows tagged `jenis="admin"` plus legacy rows matched query-time via `is_admin_fee`, grouped by date + `source_label_full`.
- **`web/bonus.py`** (`/bonus/`, "Rekonsiliasi Bonus") matches panel bonus rows against bracket bonus rows query-time — key = username (lowercase, brand prefix stripped) + rounded amount + date, greedy 1:1 per key → buckets cocok/panel_only/bracket_only + per-kategori summary. Feeds off two dedicated SourceTypes `panel_bonus`/`bracket_bonus` (parsers in `sources/parsers/bonus.py`; panel "Credit Balance" export takes ONLY bonus-prefixed Description rows and skips the net-zero `Offset` twins; bracket "Non Credit Bonus" maps code **K-BLD → "Lucky Draw"**; panel `Amt.` is ×1000, bracket `Nominal` is full rupiah). These keys are invisible to `check_completeness`/matchers/consume — the bonus path can never disturb the daily DP/WD pipeline. Display adds a query-time **kategori detail** (promo name extracted from the panel Description, e.g. "BONUS ROLLINGAN SLOT 0.5% DAILY"; bracket rows keep their mapped kategori — the two namespaces stay separate, so a cross-name pair shows as two summary rows) + a `?kategori=` filter and per-kategori value columns; none of it changes pairing (filter applies to the already-paired result).
- **`web/channels.py`** (dashboard "Metode Pembayaran" card) classifies the last batch's consumed panel rows by their raw panel **Bank Title** (client rule: contains "QR" → QRIS — including "NXPAY DEPOSIT QR"; DP order QR → e-wallet → Bank; WD order Nexuspay → QR → Bank; empty/unknown → "Lainnya", hidden at 0). Uses the same queryset as the dashboard's `panel_sum` so breakdown totals always equal the summary strip.
- **`web/rekap.py`** (`/rekap-bulanan/`, "Rekap Bulanan") meniru rekap Excel bulanan klien: 4 seksi (Net Profit / Sisa Dana Member / Total Dana Lebih Web / Selisih + penyebab) dari registry `FIELDS` (slug, seksi, kind manual/auto/carry/computed, arah tanda — SEMUA rumus hidup di modul ini, template tanpa aritmetika). Angka auto = 1 query per sumber (bonus per kategori dgn catch-all `bonus_lain` + tes konservasi, kategori FR, DP/WD dari sum `Transaction` panel langsung, hutang/piutang); carry rekursif depth-1 dari bulan sebelumnya; isian manual `RekapManual` (unik toko+periode+field, migrasi web 0002; field TANPA `choices=` by design — validasi di view) menimpa auto dengan provenance; penyebab selisih = `RekapPenyebab`; edit lewat popup HTMX pola `fr_koreksi` + OOB refresh banner kunci; param `?bulan=YYYY-MM`. Kartu dashboard **"Ringkasan Bracket"** = `ringkas_bracket_hari(toko, tanggal)` di `breakdown.py` (grouped query + overlay FRKoreksi skip-absent, tie-out persis dgn `bracket_breakdown` — dijaga tes).
- **Dashboard filter tanggal (`?dari=&sampai=`, `web/views.py` `dashboard`)**: tanpa parameter = perilaku lama (potret batch TERAKHIR) — itu kontrak yang dijaga tes. Dengan parameter, `_filter_rentang` (ladder resolusi sama dgn `/bracket/` & `/rekening/`: satu sisi kosong = 1 hari, terbalik ditukar, tanggal ngawur diabaikan) menyalakan mode jendela: `panel_sum`/`metode` = agregat `consumed_by_batch_id__in` SEMUA batch in-range, selisih & Uang periksa (D) dijumlah, tren = batch jendela, kalender ber-anchor `sampai`, runs difilter `batch__recon_date`. Kartu Bracket memakai `ringkas_bracket_rentang` (breakdown.py) yang mendelegasi ke `ringkas_bracket_hari` saat 1 hari dan meng-abs withdraw **per akun** saat rentang — supaya tie out dengan `bracket_breakdown(dari, sampai)["total"]`; overlay `FRKoreksi` ikut aturan halaman /bracket/ (hanya 1 hari). Panel **"Kerjakan hari ini" sengaja TIDAK ikut jendela** (`live_last`/`um_d_live` = batch terakhir toko): daftar kerja harus tetap hidup, kalau tidak badge jendela berdampingan dengan tombol yang cuma membuka satu batch. Mode "Semua Toko" menerima filter yang sama lewat `_dashboard_semua(request, dari, sampai)`; bracket-nya lewat `_ringkas_bracket_gabungan(toko_ids=…, rentang=…)`, dan jumlah query WAJIB tetap konstan terhadap jumlah toko di KEDUA mode (dijaga dua tes N+1).
- **`web/penjaga.py`** — three post-ingest **warnings** (never blockers) flashed by the upload-commit handler: content dates far from the date in the filename, row count far from that **stream's** habit in that toko (median of the last 10 uploads whose `kunci_aliran` matches, using `rows_parsed + rows_duplicate` = the file's real size). **The habit pool must be per-stream, not per `source_type`+`flow`** — that was v1.14.0's bug: on Vigor/TM Gaming one `panel`+`dp` bucket holds both `PANEL DP SLO` (±140 rows, pairs with the bank) and `PANEL QRIS DP SLO` (±6.900 rows, pairs with the QRIS file), and bank files pool across accounts. The mixed pool is bimodal and its median lands in the empty valley between the modes (real SLO data 03-08-2026: median 2.670), and it *shifts with upload order within one submission* — the bank-panel file was judged against 2.670 and the QRIS file a second later against 147, producing three false positives on the first real day. `kunci_aliran(nama)` derives stream identity from the uploader's own naming: strip date + extensions (including doubled `.xlsx.xlsx`), then take the **set** of remaining word tokens — a set, not a sequence, because W25 renamed `QRIS UNOPAY DP W25` → `W25 DP QRIS UNOPAY` and that must stay one stream. `flow` deliberately does NOT filter the pool (direction is already in the name; a misdetected flow would split a stream for no reason), and — gateway only — the upload's transaction keys having ~no overlap with the panel's for those dates. Real cases: a file named `01-08-2026` holding 30/06–01/07 rows (dragged SLO's panel-range floor back a month, tripping the panel-anchor gate over all of July), and a 9.156-row UNOPAY file in a toko whose habit is 615–714 whose keys matched the panel **0%** (→ 9.618 `no_panel` rows in one batch). **Warn-only is a decision, not laziness:** all three infer from habit, and habit doesn't exist for a new brand/merchant — a miscalibrated blocker would stop a toko from working until the code is fixed. Each check goes **silent when evidence is thin** (<5 prior uploads, empty comparison panel, <20 keys); a guard that cries wolf gets ignored. **The key-overlap check is additionally anchored on date AND direction** (v1.17.4): it runs only if the panel already holds rows on the file's *own* `[isi_dari, isi_sampai]` — no ±1 widening — whose `jenis` matches the upload's `flow` (mapped `dp`→`depo`; an unmapped/blank flow falls back to any direction). Without that anchor the "panel not uploaded yet" silence leaked through the ±1 widening: a gateway file landing before its panel found the pool non-empty but full of *yesterday's* panel, scoring 0% — STN 11-08-2026 accused a perfectly good NXPay file of 224/224 foreign codes, all 224 of which were in the panel ingested seconds later. Same defect class as v1.14.0: upload order within one submission must not change the verdict. The ±1 widening still applies to *collecting* the comparison keys (a late-night D-1 deposit is approved on D). Residual, documented in the module: on a toko whose same-direction panel is split across several files a day (Vigor/TMG), any one of them opens the anchor — the failure direction is a warning that fires too early, never one that gets swallowed. The checkers are **pure** (numbers/sets, not querysets) so thresholds are testable without a DB; only `periksa_upload` touches the DB and it **swallows its own exceptions** — it is called inside the commit handler's `try`, so an exception there would report a *successful* upload as failed. The panel side is read **regardless of consume status** (the panel for that date is usually already consumed) and unions `reference` + `ticket_no` (superset ⇒ fewer false accusations).
- **`web/kelengkapan.py`** `status_sumber(toko, dari, sampai)` — per-source `aktif`/`terpakai`/`batch_no`/`batch_tanggal` for the Kelengkapan Data card, **3 queries regardless of source count** (guarded by a test). Deliberately separate from the engine's `check_completeness`: that one returns booleans that get persisted into `ReconBatch.completeness`, so its shape is a contract display must not alter. It exists because "no active rows" hid three very different situations behind one grey "opsional" pill — a W25 user concluded the UNOPAY gateway was unreadable while 9.586 of its rows were already consumed by Batch #27.
- **`web/monthly.py`** (`/bulanan/`) reads `ReconBatch.summary` as-is per day (use `money`/matched, **not** `money_gross` — gross can dwarf panel). **`web/settlement.py`** (`/settlement/`) lists still-waiting credit rows via the engine's `_carried_results`. **`web/exports.py`** builds the Excel workbooks for the Export page and per-run export — `build_batch_workbook` now also appends **Breakdown Bracket** + **Rincian Rekening** sheets (old Ringkasan/Hasil sheets unchanged), and `/bracket/export/` (`export_breakdown` view) exports the breakdown table honoring the active date range + carried balances.

## Domain model conventions (critical, easy to get wrong)

All money is normalized to **rupiah** on the canonical `Transaction`. Sign and scale conventions:

- **`credit_delta`** = effect on the operator's credit ledger; **`money_delta`** = effect on real cash. A deposit is `money_delta > 0` / `credit_delta < 0`; a withdrawal is the reverse. Matching requires the two sides to share the same money direction.
- **Panel amounts are in thousands** — the panel parser multiplies by `SCALE = 1000` to reach rupiah. Don't double-apply. **Exception: COR (Gacor25) exports are already in full rupiah** — the `cor_*` parsers must NOT ×1000. COR QRIS **panel** rows have no destination-bank column, so the parser synthesizes `raw["Bank Title"] = "QRIS||"` (column `bank_title = "QRIS"`); `sources/management/commands/backfill_qris_bank_title.py` fills the same pair on rows ingested before that (structurally gated to Vigor/TM-Gaming tokos — the `"QRIS "`-description selector alone would also sweep free-text Nexus Remarks). **The empty middle segment is an engine invariant, not cosmetics — do NOT "tidy" it to a bare `"QRIS"`.** `reconciliation/engine.py` `_expected_owner` returns the middle pipe segment and falls back to the *whole string* when there is no `|`, so `"QRIS"` would hand the matcher a rail label where it expects an account-owner name, switching `_route_ok` on for the entire COR QRIS population (it is a secondary sort key in pass 1's greedy 1:1 assignment — silently different pairings, no error anywhere).
- **`QRFlyerParser` resolves columns through an ALIAS map (`_ALIAS`) compared on NORMALIZED names, not per-shape branches** — the vendor has renamed its headers **four** times since August 2026 and a fifth is a matter of when, not if. Canonical field ← candidate names, priority-ordered: ticket ∈ {`TXN ID`, `transaction_id`, `Transaction Id`}, ref ∈ {`Client Reference`, `Client Reff`}, username ∈ {`Customer ID / User Account`, `username`, `Username`}, amount ∈ {`Transaction Value`, `total_amount`, `Amount`}, created ∈ {`Transaction Date`, `trans_date_time`, `Created At`, `date`}, settled ∈ {`Settlement Time`, `bot_success_time`, `Callback`}, fee ∈ {`Fee`, `charges`}. **`_norm` strips case and every non-alphanumeric before comparing, and the comparison is EXACT on the normalized form — never substring.** Normalization is what absorbs a whole class of rename without a release (`Date`/`date`/`DATE`, `total_amount`/`Total Amount`, `client_reference`/`Client Reference` all collapse to one entry — which is also why the alias tuples no longer list case/underscore variants separately). Exact-not-substring is load-bearing in the other direction: `net_amount` normalizes to `netamount` and must never be caught by `amount`, or every row lands short by the fee, pass 0 fails on amount, and nothing anywhere errors. All four shapes are **WIB**, and shape 4 was proven independently rather than assumed from its predecessors — LTN 12-08-2026, 339 rows: panel approves a median **+3s** after `date` (p10/p90 +2/+6), with **zero** negative deltas; a ZPay-style +7h shift would flip all 339 negative and block pass 0 via the directed window. `row_hash` keeps ONE recipe (`[ticket, ref, amt]`) across every shape, so a day re-exported in a new format dedups instead of double-counting (pinned by a cross-shape test).
- **`_WAJIB` header guard — the load-bearing defense, and the three Flyer failures are NOT the same bug.** Shape 2 (snake_case) had neither `TXN ID` nor `Client Reference`, so every row looked like a footer → *zero* rows, a "successful" upload with nothing in it. Shape 3 kept `Client Reference`, so rows were **not** skipped: the parser emitted 1.519 fully-formed rows with `ticket_no=""`, `amount=0`, `posted_date=None`. **Junk that gets through is far worse than nothing — it claims to be data.** Before this was caught, five uploads across four tokos had written **6.118** such rows to production (inert: 0 consumed, 0 `MatchResult`, `posted_date` NULL keeps them out of every date window — that is luck, not design). So the guard is at the HEADER, not the yield: if the ticket or amount column fails to resolve, `parse` **raises**, naming the headers actually present and the aliases it knows. Same certainty-class blocker as ZPay's zero-yield guard (columns absent is a fact, not habit-inference), but it must stay header-level — a yield-based guard cannot see this failure. **Shape 4 (LTN 12-08-2026) then defeated that guard by satisfying it:** `transaction_id` and `total_amount` were both already known, so ticket and amount resolved correctly and the guard passed in silence — only the time column (`date`) was unrecognized. That alone was enough. `occurred_at` NULL hides a row from the engine (which filters `occurred_at__date`) and `posted_date` NULL hides it from every report page, so 339 LTN panel rows sat at "Belum ada uang masuk" while their money was already in the database; production held **1.705** such rows (LTN 339, BSW 1.366) on top of the 6.118. Hence `_WAJIB_WAKTU`: created **or** settled must resolve, "or" because `posted_date = (settled or created)`. Detection gained real signatures for shape 3 (`client reference` + `rrn` + `callback` → 0.95) and shape 4 (`client reff` + `total_amount`/`net_amount` → 0.95); both previously rode the filename rule alone at 0.85. Note `client reff` is not a substring of `client reference` (11th char `f` vs `e`), so the two rules cannot collide. Calibrated: 06-08-2026 M25 120/120; HKW 01-08-2026 **1518/1519 `cocok` reason `ticket`**; LTN 12-08-2026 **339/339** on ticket AND amount, lifting that day's Panel↔Bank run from 674/1148 to 1002/1148 with **zero** QRISFLYER rows left unmatched.
- **`sources/services.periksa_hasil_bertanggal` — the cross-parser generalization of that lesson, and it belongs to every parser, not just Flyer.** A per-parser header guard only protects the parser that already learned the new shape; this one catches the failure *class* in one place: rows came in, and not one of them carries `posted_date` **or** `occurred_at` → `ingest` raises **before anything is written**. Requiring BOTH columns empty across ALL rows is deliberate — a row missing both is unusable by construction (invisible to matcher and reports alike), whereas partly-dateless rows can legitimately be footers or pending entries. The production evidence that the 100% threshold is safe: of 6,1 million rows, exactly one dateless row exists outside the Flyer incidents. This is a **certainty** blocker like ZPay's zero-yield guard, not a habit inference like `web/penjaga.py` — "rows in, none usable" needs no history to judge, so it cannot falsely accuse a new brand. Its message explicitly tells the operator **not** to re-upload (the result would be identical) and to send the file to the developer instead.
- **`manage.py perbaiki_gateway_tanpa_tanggal` repairs already-ingested dateless gateway rows in place, from `raw`** — parser fixes are never retroactive, and `raw` preserves every original column including the time one that was unrecognized. **Re-uploading is NOT the recovery path** and this is the subtle part: the old `row_hash` was computed while `reference` was still empty, so the same file re-parsed now yields a *different* hash and lands as new rows — the day counts twice. The command therefore recomputes `row_hash` with the parser's exact recipe **and derives ticket/ref/amount from `raw` through the same expressions**, not from the DB columns, so `str(Decimal)` can't drift between the two paths. Structural gates: `source_type=gateway` + both time columns NULL + `ticket_no != ""` — that last one is what separates the 1.705 repairable rows from the 6.118 shape-3 junk, which it deliberately never touches (deleting those is the data owner's call). Rows whose recomputed ticket/amount disagree with what is stored, and rows whose new hash collides with an existing one (a correct copy already landed), are skipped and **reported per cause** — a command that writes must be loud about what it declined to write.
- **`ZPayParser`** (`zpay`, `gateways.py`) — QRIS ZPay/ZETPAY CSV (BOM), panel-Nexus brands. `Tiket Number` (D…) == panel ticket → pass 0; `Order ID` is `<BRAND>-<username>-<random>` so the username comes from the **middle** segments rejoined (a plain `split("-")[1]` truncates hyphenated usernames); `Nilai` is gross (= `Fee` + `Sub Total`, pinned by a test) and matches what the panel records. **`Status` carries THREE money values — `paid`, `settled` and `done` — and `STATUS_UANG` whitelists exactly those.** `paid`/`settled` are one lifecycle (paid, then disbursed); `done` is the vendor's **renamed** wording from ~07-08-2026 on, shipping alongside a separate `Status Settled` (Settled/Unsettled) column. `unpaid` is the deliberate exclusion — an abandoned QR, proven on 42/42 rows carrying no ticket, no `Paid At`, no RRN — and `STATUS_BUKAN_UANG` names it **only** so the zero-yield message can tell an all-`unpaid` file ("no successful payment in here, check the period") apart from a genuinely foreign status ("report it so the list can grow"); it never decides which rows pass. That split is not cosmetic: without it an all-`unpaid` export invites the operator to report a renamed status, and adding `unpaid` to the whitelist would **fabricate money** out of QRs nobody ever paid. Two renames in two months, both caught the same way: v1.17.1 filtered `== "paid"` alone and swallowed 69 `settled` rows; v1.17.3 rejected the whole 11-08 STN file over `done`. Don't extend the list speculatively; the protection against a fourth value is the **zero-yield guard** — if the file holds transaction rows (Order ID or ticket present) but none pass, `parse` **raises** naming the statuses it found, and the upload handler shows that message. That blocker does *not* contradict `web/penjaga.py`'s warn-only rule: penjaga infers from habit, this is a certainty (rows in, nothing out). A file with no transaction rows still returns `[]` legitimately. A blacklist would be the dangerous inversion — an unknown status let through **fabricates money**, whereas one held back merely surfaces as a panel row without money. Note the guard only fires at *zero* yield: a file mixing a known status with a renamed one loses the renamed rows silently (pinned by `test_sebagian_status_asing_tidak_melempar`) — tolerable only because ZETPAY settles in one 09:00 batch, so real files are single-status. **The vendor's timestamps are UTC while this whole app is naive WIB — the parser shifts `occurred_at`/`posted_date` by `UTC_KE_WIB` (+7h) and leaves `raw` at the vendor's original values.** Do NOT remove that shift: without it the money row predates its own credit row by 7 hours, and the engine's *directed* date window (money ≥ credit) then **blocks pass 0 outright** — the failure is a blocked pair, not merely a wrong day. The proof is layered and admits no alternative: on the 06-08-2026 sample the panel covers 06-Aug in full and holds 69 QRISZPAY rows, yet **none** of the file's 48 `Order ID`s appear in it; the ticket blocks are disjoint and adjacent (panel ends D770354, file starts D770355) on a counter the panel shares across channels; and after the shift D770355 lands 1m44s after D770354, where unshifted it *precedes* it by 7 hours. `row_hash` excludes time, so the shift cannot double-count a re-ingest — but by the same token a wrongly-dated ingest could never be corrected by re-uploading, which is why this landed before the parser's first deploy. **Pairing is proven** (v1.17.2): the operator's re-request produced the real 06-Aug export — 69 rows, tickets D770214–D770354 — matching the panel **69/69 on ticket, Order ID, AND amount**, with the panel approving a median **3 seconds** after ZPay's `Paid At`+7h (unshifted that gap would be 7h in the wrong direction). End-to-end through `validate_brands` it is 69/69 `cocok` reason `ticket`, lifting the 06-08 M25 batch from 641/724 to **710/724**. The first sample (48 rows, D770355–D770434) is genuinely 07-Aug WIB 00:01–06:52 traffic and correctly produces no results in the 06-Aug batch — it waits for the 07-Aug one. The `done`-era file re-proves every one of those properties independently (v1.17.4, STN 11-08-2026, 607 rows → 565 `done`): **564/564** against the panel on ticket, amount, username AND `Order ID` present in the panel's `Remarks`, panel approving a median 3s after `Paid At`+7h (unshifted: 25.203s the wrong way), and end-to-end `validate_brands` lifting the day's Panel↔Bank run from **360/943 to 924/943**. The 565th row (D3298751, paid 23:59:59 WIB) belongs to the 12-Aug panel and correctly lands as `no_panel` in the 11-Aug batch. DP-only — no WD sample exists yet, in any status wording.
- **Per-brand exact keys on the money side** (prefer these over fuzzy): COR QRIS `Transaction ID` (UUID) == gateway `OrderId` → `reference`; MUL QRIS-HOKI `Whitelabel Transaction ID` == panel ticket; MXW QRFlyer `TXN ID` / NXPay `Ticket Number` == panel ticket; UNO QRIS-WD `Order ID (Merchant)` (UUID penuh) == panel Vigor/TMG WD `Transaction ID` (parser `cor_qris_wd_gateway`, REFUND rows dilewati). RPay (MUL/M77) sengaja TANPA `reference` — anchor = `Customer Username` == username panel; UUID hanya di `raw` karena Remarks panel Nexus terbukti tidak memuatnya (aturan blocked engine akan mengasingkan reference tak dikenal panel). BBS RafflesPay varian XLSX: DP `rpay_xlsx` (`Ticket Number` D... == panel; RRN hanya di raw, ada duplikat nyata) dan WD `rpay_wd_xlsx` (header dua-tingkat, `Ticket` W... == panel, hanya `Transfer=success`, `Disbursed Amount` = uang keluar). Some COR exports lack the xlsx `<dimension>` tag and have broken stylesheets — read them with the styles-tolerant raw reader in `sources/parsers/base.py`, not plain openpyxl.
- **Fee rows are tagged `jenis="admin"`** and deliberately excluded from WD money totals, matching, and completeness (they aren't real withdrawals): BCA `BIAYA TXN` rows, and BRI **BRIVA** fee rows (each BRIVA e-wallet WD pairs with an identical-description Rp1.000 debit twin, `is_briva_fee`). BRI `ATMSTRPRM…`@6500 / `BFST…`@2500 / `BRIVA…`@1000 and Mandiri `Biaya…` are now flagged via `sources/parsers/fee_rules.is_admin_fee` (used both by the parsers at ingest and, query-time, by the Rincian Biaya report for legacy rows ingested before the rule existed).
- **WD e-wallet via BRI (BRIVA)**: mutasi shows `BRIVA<channel code><phone>` glued together (DANA 88810, GOPAY 30135, OVO 88099, SHOPEEPAY 112, LINK AJA 91188) — the 16-18 digit run defeats the generic 9-15 digit phone scan, so `_money_phones` has a dedicated `_BRIVA_RE` that strips the code before phone matching. Client's channel-trace matrix ("TRANSAKSI KELUAR MUTASI WITHDRAW") is the source of truth for which bank→channel combos carry identity at all (e.g. BNI→GOPAY carries NO number — unmatchable by identity).
- Match keys on `Transaction`: `ticket_no` (panel `D…`/`W…`), `reference` (gateway), `username`, `counterparty` (bank sender/receiver name). Names are isolated per-source in the parser; the engine only normalizes + fuzzy-matches.
- `USE_TZ = False` — bank/panel timestamps are naive local (WIB, `Asia/Jakarta`). Don't introduce tz-aware datetimes.

## Access control (`web/access.py`)

RBAC is scoped **per Toko** (brand/site). `tokos_for(user)` is the single source of truth: admins/supervisors see all active Tokos; auditors see only `allowed_tokos`. The custom user model is `accounts.User` (roles: admin/supervisor/auditor; no public signup). The active Toko lives in the session (`active_toko_id`) and is injected into every template by the `web.context_processors.toko` context processor. **Mode "Semua Toko" (khusus admin):** session boleh berisi sentinel `"all"` — `_active_toko` WAJIB tetap mengembalikan objek Toko nyata (guard mengembalikan toko pertama yang diizinkan; jangan pernah biarkan `"all"` menyentuh query — `filter(id="all")` crash di Postgres), context processor men-set flag `semua_toko` (via `web.access.mode_semua`), dashboard beralih ke template terpisah `dashboard_all.html` (agregat lintas toko TANPA loop query per-toko — dijaga tes assertNumQueries konstan), Hutang/Piutang menerima ceklis multi-toko `?toko=` (kosong = semua, disaring `tokos_for`), dan halaman lain menampilkan bar penjelas — `semua_toko_page=True` menandai view yang sudah sadar-mode (bar hilang), `semua_toko_tulis=True` memakai varian peringatan di halaman tulis (upload/rekonsiliasi/rekap/bracket). `Toko.panel` (nexus/vigor/tm_gaming, wajib saat membuat toko) mengelompokkan kedua picker via `tokos_grouped` (optgroup, 0 query ekstra). Web views live in `web/views.py` (reconciliation flow) and `web/admin_views.py` (Toko/user management, deletes).

## Performa (v1.18.0 — jangan dibongkar tanpa mengukur ulang)

Data produksi tumbuh ke **6,1 juta baris / 10 GB** (±185 rb baris/hari). Dashboard toko terbesar sempat **14,6 dtk**, 11,3 dtk di antaranya SQL. Empat keputusan di bawah yang menurunkannya, semuanya **tanpa mengubah satu angka pun di layar** — kalau ada yang tampak "tidak rapi", baca alasannya dulu.

- **Dua index komposit `(toko, source_type, posted_date)` dan `(toko, source_type, occurred_at)`** (`transactions/models.py` Meta, dinamai eksplisit `tx_toko_src_posted_idx`/`tx_toko_src_occurred_idx` karena nama itulah yang dipakai runbook DDL manual). Urutan kolom disengaja: dua kolom pertama selalu KESETARAAN di semua pemakai, tanggal RENTANG di posisi terakhir. Sebelum ini, mencari baris bracket satu hari untuk satu toko menemukan 306 rb baris lalu membuang 99 rb hanya karena tanggal — 767 MB heap, bitmap sampai *lossy*. Ukuran nyata di prod jauh di bawah perkiraan (**42 MB** dan 221 MB) berkat deduplikasi btree Postgres 13+.
- **`core/db_ops.TambahIndexAman` ada karena `AddIndexConcurrently` bawaan Django MEMBUNUH seluruh suite.** Ia memanggil `schema_editor.add_index(..., concurrently=True)` tanpa memeriksa vendor; tanda tangan SQLite (`django/db/backends/base/schema.py`) tak punya argumen itu → `TypeError` saat **pembuatan DB tes**, jadi yang mati bukan satu tes melainkan 1.600+. Kelas ini: non-Postgres → `AddIndex` biasa; Postgres → periksa `pg_index` dulu (ada & valid = no-op, INVALID = WARNING berisi perintah pemulihan), dan **tidak pernah menggagalkan boot** — index hilang berarti halaman lambat, bukan angka salah, dan aplikasi mati jauh lebih mahal. `index.create_sql(..., concurrently=True)` juga melempar di SQLite, jadi DDL runbook = keluaran SQLite + kata `CONCURRENTLY` disisipkan manual. Index produksi dibangun lebih dulu lewat psql karena start command Railway menjalankan `migrate` SEBELUM gunicorn membuka port; kalau langkah itu terlewat migrasi tetap membuatnya — lambat, tapi benar.
- **Kartu "Transaksi per Sumber" di-group pada `source_type_id`, BUKAN `source_type__name`** — yang terakhir memaksa JOIN dan menyeret jutaan baris ke hash join (dulu: Parallel Seq Scan 6,1 juta baris / 5,3 GB untuk satu diagram batang). Nama/key diambil dari tabel referensi belasan baris, dan **`tx_total` diturunkan dari hasil yang sama** supaya invarian `{% widthratio s.n tx_total 100 %}` benar secara konstruksi. **Agregat `Upload.rows_parsed` sudah dipertimbangkan dan DITOLAK** meski tie-out-nya 126/126 di produksi: kecocokan itu membuktikan jalur divergensinya belum pernah dijalankan, bukan bahwa jalurnya aman (hapus transaksi lewat Django admin tak pernah memperbarui `rows_parsed`). Angka di layar tetap fakta terukur; ±0,15 dtk tak sepadan.
- **Nomor batch kalender dashboard memakai `bisect` atas SEMUA id batch toko** (`web/views.py`), bukan daftar `batches` yang ada di memori — daftar itu tersaring `recon_date__isnull=False`, sedangkan nomor urut menghitung batch tanpa tanggal juga (konvensi sama di `web/kelengkapan.py`). Memakai daftar tersaring akan **menggeser nomor batch**. `bisect_right(terurut, x) ≡ COUNT(id <= x)`.
- **`web/rekening.py` memakai rentang datetime setengah-terbuka, bukan `occurred_at__date__range`** yang lebih enak dibaca: `__date__` membungkus kolomnya (`CAST(... AS DATE)`) sehingga index btree mana pun atas `occurred_at` mati. Setara persis karena `USE_TZ=False`. Dikunci `test_batas_tengah_malam_ikut_terhitung`.
- **`_carried_results` (`reconciliation/engine.py`) meng-`select_related("run__batch__tolerance")` meski engine sendiri tak memakainya** — `web/settlement.py` membacanya per baris; tanpa itu halaman Settlement 439 query. Jangan dibuang karena tampak tak terpakai.
- **Setelan Postgres produksi** (via `ALTER SYSTEM`, tersimpan di `postgresql.auto.conf`, batal dengan `ALTER SYSTEM RESET <param>` + reload): `random_page_cost=1.1` (nilai bawaan 4 mengasumsikan piringan berputar dan itulah yang membuat perencana menolak index), `work_mem=32MB`, `max_wal_size=2GB`, `effective_cache_size=16GB`, `jit_above_cost=1e6` (sengaja BUKAN `jit=off` — JIT tetap berguna untuk query analitik panjang di matcher). `shared_buffers` masih 128 MB bawaan; menaikkannya butuh restart dan **belum** dilakukan. Setelah mengubah setelan perencana, WAJIB `EXPLAIN` query mesin (pool aktif matcher, carry-over, anchor ticket) — halaman laporan tidak mewakili jalur rekonsiliasi.
- **Gunicorn `--workers 4 --threads 8`.** gthread menyimpan koneksi DB per-**thread** dan `CONN_MAX_AGE=600` menahannya, jadi batas atas koneksi = workers × threads = 32 dari `max_connections=100`. `core/tests_start_command.py` menjaga `Procfile` ↔ `railway.json` identik dan aritmetika itu sebagai pagar yang dieksekusi.
- **Urutan pencocokan WAJIB deterministik — jangan buang `order_by("id")` di `sides()` maupun pemecah seri `(-left.id, -right.id)` di pass 1 & 3.** Tanpa keduanya, hasil rekonsiliasi bergantung pada rencana eksekusi Postgres: `sides()` dulu tak punya `order_by`, `Transaction.Meta` tak punya `ordering`, dan kunci sort pass 1 `(skor, route, -delta)` tidak total — sehingga seri dipecahkan oleh urutan queryset. Terbukti: satu pemain, 4 baris nominal sama, urutan `[P1,P2]` → cocok=1 vs `[P2,P1]` → cocok=2. Menambah index (atau sekadar pertumbuhan data yang menggeser statistik) menggeser jumlah "Cocok" untuk data yang SAMA. Pemecah seri sengaja dipilih agar mereproduksi urutan de-facto lama — 199 tes reconciliation lolos tanpa satu pun disesuaikan. Yang ditetapkan hanya SIAPA yang menang saat seri, bukan siapa yang boleh berpasangan. Sisa yang belum dibereskan dan sudah diketahui: `PanelBracketMatcher._match_ticket` memakai `next(...)` greedy, jadi saat satu ticket dobel di bracket, baris mana yang diklaim masih bergantung urutan masukan (kini stabil lewat lapis 1); pass 2 memilih `best` dengan `>` ketat + `break`, determinismenya bersandar penuh pada lapis 1.
- **`+ timedelta(days=N)` pada tanggal dari input pengguna WAJIB lewat `_geser_hari()`** (`web/views.py`; kembarannya disalin di `web/settlement.py` karena `views` sudah mengimpor `settlement` — impor balik melingkar). `date` Python hanya mewakili 0001-01-01…9999-12-31 dan melewatinya melempar `OverflowError` **di Python, sebelum query dibentuk** → HTTP 500 untuk seluruh view. Ini bukan URL rakitan: tiap bar filter memakai `<input type="date">` tanpa `min`/`max`. Satu jalur bahkan tanpa parameter apa pun — `next_date` digeser dari `recon_date` batch terakhir yang berasal dari tanggal panel hasil ingest, jadi satu tanggal rusak di data mematikan dashboard toko itu permanen. `web/penjaga.py` sengaja dikecualikan: `periksa_upload` membungkus dirinya `try/except`, jadi akibat terburuknya satu peringatan hilang.
- **`python manage.py periksa_index`** melaporkan index yang HILANG atau INVALID pada `transactions_transaction` dan keluar non-nol bila ada. Ini ADA karena `TambahIndexAman` menelan kegagalan build: `record_migration()` tetap dipanggil begitu `apply()` tidak melempar, jadi migrasi tercatat selesai dan index tak akan pernah dibangun ulang sendiri — halaman lambat diam-diam. Jalankan setelah tiap deploy yang menyentuh index.
- **Backlog dengan bukti, sengaja TIDAK dikerjakan di v1.18.0:** ~870 MB index mati (`row_hash_like` 735 MB, `username_like` 74 MB, `account_id` 61 MB — `idx_scan=0` selama 5 minggu penuh, statistik tak pernah direset) — menghemat disk & mempercepat tulis, bukan mempercepat halaman, dan membuang index `_like` menciptakan penyimpangan skema yang tak dimodelkan Django. Juga: agregat m2m `duplicate_transactions` di Mutasi Bank, dan partial index untuk 5× EXISTS `check_completeness`.

## Deployment

Railway (Nixpacks), config in `railway.json` / `Procfile`. Production is triggered by env: `DATABASE_URL` present → Postgres via `dj-database-url` (else sqlite); `RAILWAY_PUBLIC_DOMAIN` auto-populates `ALLOWED_HOSTS` + `CSRF_TRUSTED_ORIGINS`; `DEBUG=False` turns on the SSL/HSTS/secure-cookie block. Static files served by WhiteNoise (compressed manifest storage). Start command runs `collectstatic` + `migrate` + gunicorn.

## Versioning

`core/version.py` is the **single source of truth**: a `RILIS` tuple of `Rilis` dataclasses, newest first, whose top entry defines the running version. It feeds the sidebar/login badge (`core.context_processors.versi` → `app_versi`/`app_rilis`), the `/versi/` Riwayat Versi page, the `Versi aplikasi` row stamped into every exported workbook's Ringkasan sheet, and `CHANGELOG.md`.

**Shipping a user-visible change means adding a release entry** — prepend a `Rilis(...)`, run `python manage.py changelog`, commit both. `core/tests_version.py` fails the suite if `CHANGELOG.md` drifts, if the ordering/date sequence breaks, or if a release's declared `jenis` doesn't match its number jump (mayor→X+1.0.0, minor→x.Y+1.0, patch→x.y.Z+1).

Scheme (spelled out in the module docstring, including the explicit 2.0.0 criteria): MAYOR = the way the app works changes fundamentally; MINOR = a new capability worth announcing; PATCH = pure fixes; 0.x = pre-production. **New banks/gateways/brands, new report pages, and tighter access control stay MINOR no matter how many** — that rule is what keeps the numbering meaningful.

Release boundaries are drawn on **contiguous commit ranges** (one release = one whole date window, never interleaved), which is what makes the retroactive 0.1.0–1.9.0 map verifiable: the 15 commit-bearing releases tile all 281 commits exactly, no gaps, no overlaps. Preserve that property when adding entries. Business-language summary for management: `docs/ringkasan-versi-2026-07-25.md`.

## Working notes

- Design specs and implementation plans for completed features live in `docs/superpowers/{specs,plans}/` — check there for intent behind non-obvious decisions.
- `db.sqlite3` is the local dev DB and is **gitignored** (contains real working data — never commit it). Git worktrees don't have it; copy it from the main checkout + `migrate` if a preview needs real data.
- Tests that GET-render a template extending `web/base.html` need a `collectstatic`-generated `staticfiles.json` manifest (WhiteNoise `CompressedManifestStaticFilesStorage`), which is **gitignored**. Fresh worktrees/CI fail such tests with `ValueError: Missing staticfiles manifest entry for ...` until you run `python manage.py collectstatic --noinput` once. Same class of gap as `db.sqlite3`.
- **Git flow:** commit per work chunk AND push to `origin/main` (fast-forward only, never force). A teammate (`sabian`) also lands on main — always `git fetch` + rebase before pushing.
- **Pushing does NOT deploy.** Deploys are manual: `railway up --ci` run from the main checkout `/Users/macads/Truth-of-auditor` after fast-forwarding it to `origin/main` (running it from a worktree ships a stale tree). Never deploy without explicit confirmation — this is a live financial app.
- **Geo-block (K4) is LIVE in prod (2026-07-22): KH-only.** `web/middleware.GeoBlockMiddleware` + `geoip2fast` (bundled country DB, no key/network). Controlled entirely by Railway env vars (code default is OFF): `GEO_BLOCK_ENABLED=true`, `GEO_BLOCK_COUNTRIES=KH` (allow-list of ISO codes), `GEO_BLOCK_BYPASS_STAFF=true`, optional `GEO_BLOCK_ALLOWLIST` (IP/CIDR break-glass). Real client IP di-resolve rantai helper `_client_ip` (X-Forwarded-For paling-kiri, pasca e4a055b — BUKAN lagi `X-Envoy-External-Address`) → `_ip_is_internal` → `_via_cloudflare` (opsional `GEO_BLOCK_REQUIRE_CF`) → `_real_client_ip` → `_ip_in_allowlist`; private/loopback (health checks) and the allowlist always pass. Rantai helper yang sama dipakai ulang `IPAllowlistMiddleware`. **Break-glass if the Cambodia team gets locked out:** `railway variables --set GEO_BLOCK_ENABLED=false --service web --environment production` (instant, independent of app HTTP). Because it blocks non-KH, you cannot smoke-test prod over public HTTP from outside Cambodia (you'll get the 403 "Trust No One" page) — verify via `railway ssh` container checks instead.
- **Filter berbasis JSON di WHERE butuh `Cast`.** `KeyTextTransform("Bank", "right__raw")` yang dibandingkan langsung dengan string membuat Django membungkus sisi kanan sebagai JSON (`… = JSON_EXTRACT('BANK BCA | HENDI | WITHDRAW','$')`) → SQLite menolak dengan `malformed JSON` (nama akun bukan dokumen JSON). Bungkus anotasinya `Cast(KeyTextTransform(...), TextField())` — lihat `web/views.py` `_chips_sumber_uang`, yang mengisi chip "Filter bank/sumber" tab **Tidak Ada di Panel** untuk `run_detail` + `review_queue`: baris uang bank/gateway dilabeli dari upload (`specific_source_label`), baris **FR/Bracket** dari `raw["Bank"]` — karena `specific_source_label` sengaja mengembalikan "Bracket" generik untuk panel/bracket, dan chip satu-pilihan itu percuma (keluhan klien 2026-07-27, relasi panel_bracket panel Vigor/TM Gaming).
- Django 5.2 keeps the cached template loader on even in DEBUG — restart the dev server after editing templates before concluding an edit "didn't work".
- Django `{# #}` comments are **single-line only** — a multi-line one leaks into the rendered page (twice now; the Paket I leak contained the literal word `<template>`, which became a real tag and swallowed the entire body while the test suite stayed green). Use `{% comment %}…{% endcomment %}` for anything longer. Guarded by `web/tests_template_hygiene.py`.
